    Part 1: Motion Planning in Simulation¶

    Equipment List for Software¶

    1. Microsoft Visual Studio Code for Python. Download and install from Microsoft Visual Studio Code. Set up Python using this video and test a simple script the same way it's shown there: youtu.be/9o4gDQvVkLU.
    2. Install additional Python packages. Packages can be installed by typing the following in the "terminal" in Visual Studio Code:
    python3 -m pip install {package_name}

    Run this command three times with {package_name} replaced with numpy, matplotlib, and opencv-python. This minute-long video shows how to install a package: youtu.be/sQPgR1Fz67c.

    1. Multi-Joint dynamics with Contact (MuJoCo). Install the MuJoCo Python package by typing the following in the terminal inside Visual Studio Code:

    python3 -m pip install mujoco
    4. Vibe coding with LLMs. It's highly recommended that you use LLMs (ChatGPT, Gemini, Claude, etc.) to vibe code. Vibe coding is a style of software creation where you use natural-language prompts to direct an LLM to write, fix, and build code, rather than typing it yourself line by line. You don't need a paid version of any LLM — the free tier is enough.

    General advice: break the problem down into simple tasks, then assign the LLM to program each task one at a time. Run multiple tests after each task to make sure the output does what you expect, and save your working code before you ask the LLM to add more features.

    Understanding the Files Given to You¶

    Overview¶

    Download the folder autonav.zip and unzip it. You'll see the Python file template_mecanum.py. It calls into a set of routines in MentorPi_hw (for hardware, covered in Part 2) and MentorPi_sw (for the simulator). In this section we work only with simulation:

    PLATFORM = "sw"

    Motion¶

    Mecanum wheels let a robot drive forward/backward, sideways, and turn — all independently — by spinning four rollered wheels at different speeds. Read about how they work here: Moving with Mecanum Wheels (SunFounder).

    You command the robot's motion with three numbers: forward/backward speed vx, sideways speed vy, and turning rate wz. For example:

    vx = 1
vy = 0.5
wz = 1.0
robot.set_velocity(vx=vx, wz=wz, vy=vy)

    Each run also defines a goal position in its scene XML file, which you can read with:

    goal_x, goal_y = robot.get_goal()

    and the robot's own position and heading at any instant come from:

    x, y, theta = robot.get_pose()

    Lidar Sensor¶

    A 2D lidar spins a laser beam around the robot and measures the distance to whatever it hits at each angle, building a ring of range readings around the robot. Read more here: LiDAR Processing Overview (MathWorks).

    Turn the lidar on with:

    flag_lidar = True

    and read/visualize it with:

    points = lidar.get_data()
lidar.show()

    points holds every point the lidar detected on that sweep, given in the robot's own frame (not the world frame): points.x_data is meters ahead of the robot, points.y_data is meters to the left (positive) or right (negative), and points.angle_data is the angle to that point in degrees, where 0° is straight ahead and positive angles are counterclockwise (to the left). All three are lists of the same length — one entry per detected point — so points.x_data[i], points.y_data[i], points.angle_data[i] together describe the i-th detected point, and len(points.x_data) tells you how many points were detected. Beams that hit nothing within lidar_range_to_see_in_meters are left out, so you won't get a fixed number of points every call — check for an empty result before indexing into it.

    Run the simulation and you'll see the lidar view appear. You can tune these parameters in the code:

    lidar_field_of_view_degrees = 90.0   # angular span the lidar scans, centered on the robot's forward direction
lidar_range_to_see_in_meters = 3.0   # maximum distance, in meters, the lidar can detect an obstacle
lidar_num_beams = 180                # number of individual beams spread across the field of view (angular resolution)

    Camera Sensor¶

    An RGB-D camera captures a normal color (RGB) image plus a depth image, where each pixel's value is its distance from the camera instead of its color. Read more here: RGB-D Images: A Comprehensive Overview (GeeksforGeeks).

    Turn the camera on with:

    flag_camera = True

    and read/visualize it with:

    frame = camera.get_data()
camera.show()

    frame holds the RGB and depth images captured together, plus a convenience reading:

    • frame.rgb — a (camera_height, camera_width, 3) array of 0-255 color values (a normal color image).
    • frame.depth — a (camera_height, camera_width) array where each pixel is that point's distance from the camera plane, in meters (not a 0-255 value). This is depth, not straight-line range from the camera — the two only agree exactly at the center pixel.
    • frame.center_depth — a single number: the depth, in meters, at the pixel right in the center of the frame. Handy when you just want "how far away is whatever the robot is looking straight at" without indexing into frame.depth yourself.

    Run the simulation and you'll see the camera view — both RGB and depth. You can tune these parameters in the code:

    camera_width = 320    # captured frame width, in pixels
camera_height = 240   # captured frame height, in pixels

    Exercises in Simulation¶

    The objective is to avoid obstacles while reaching a goal. Obstacle positions come from the lidar and camera as distances from the robot in the local (robot) frame — that is, measured relative to the robot. The goal position is given in the world frame — that is, measured relative to the world.

    A heuristic go-to-goal controller¶

    "Heuristic" means a controller built from practical experience or intuition rather than a formal optimization. One control idea is given below — feel free to try your own instead.

    You have two natural choices of control inputs: vx, vy (straight + sideways motion) or vx, wz (straight motion + turning). Start with vx, vy — it's easier to reason about — and extend to vx, wz afterward if you'd like.

    A simple way to steer toward the goal is to compute the direction from the robot's current position \((x, y)\) to the goal \((x_g, y_g)\):

    \[ \phi_g = \operatorname{atan2}(y_g - y,\; x_g - x) \]

    (subtract the robot's heading \(\theta\) if you want this angle expressed in the robot's own body frame instead of the world frame). Then set the ratio of sideways to forward speed from that angle:

    \[ \frac{v_y}{v_x} = \tan(\phi_g) \]

    Set vx to a small value, e.g. vx = 0.1, and compute vy = vx * tan(phi_g). Once this works, ramp up vx to get the robot moving faster.

    Adding obstacle avoidance¶

    Extend the same idea to avoid obstacles. Compute the direction from the robot's current position to the nearest detected obstacle, \(\phi_d\), and steer using:

    \[ \frac{v_y}{v_x} = \tan(\phi_g + \delta) \]

    where \(\delta\) is an offset angle you choose from roughly \(-90°\) to \(90°\) (but not \(0°\)), with its sign chosen based on which side the obstacle is on. This biases the robot's heading away from the obstacle while it continues generally toward the goal.

    Suggested order of attack:

    1. Start with the lidar sensor and command vx, vy as shown above.
    2. Once that works, swap the lidar sensor for the camera.
    3. Try the vx, wz control combination as well.

    Standardized testing with BARN¶

    Once you're ready, test your controller on standardized environments from BARN — Benchmark Autonomous Robot Navigation. BARN is a public benchmark of 300 procedurally generated, simulated obstacle courses spanning a range of difficulty (from sparse obstacles to tightly packed, maze-like clutter), used to compare ground-robot navigation approaches on a common, standardized set of environments.

    To generate an environment proceed as follows. First, download BARN_dataset.zip. Then unzip it and note its location on your system (e.g., /Users/<name>/Downloads/) and put this folder name in the appropriate place in barn_to_mujoco.py.

    Finally, set the BARN_num variable in barn_to_mujoco.py and run the script. This generates the environment inside the BARN folder. Copy the path to the resulting scene_<no>.xml into your Python script and run it, where <no> is the BARN environment number.

    Try a principled controller¶

    After you're comfortable with the heuristic controller on simple environments and on BARN, pick one of these more principled controllers to implement:

    • Dynamic Window Approach (DWA)
    • Artificial Potential Field
    • Timed Elastic Band
    • Model Predictive Control

    Program it against the simple environment first, then against BARN, and compare its performance to your heuristic controller.
