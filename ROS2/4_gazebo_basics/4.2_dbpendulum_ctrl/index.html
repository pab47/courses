4.2 dbpendulum_ctrl¶

Package download

Download dbpendulum_ctrl.zip

Same double pendulum as 4.1 dbpendulum, now actuated: a feedback-linearization (computed-torque) controller tracks a point-to-point reference trajectory, emulating the course's 4b_doublependulum_trajectory_tracking/twoink_main.py reference script. Unlike dbpendulum, motion here is commanded, not passive — the pendulum starts at rest and smoothly moves through a planned trajectory instead of swinging chaotically under gravity alone.

Install prerequisite¶

sudo apt update
sudo apt install ros-jazzy-ros-gz
sudo apt install ros-jazzy-ros2-control ros-jazzy-ros2-controllers ros-jazzy-gz-ros2-control

The first line is the same Gazebo/ROS2 bridge dbpendulum needs. The second adds ros2_control and gz_ros2_control, which this package uses to send torque (effort) commands into Gazebo — dbpendulum never needed these, since it has no actuation at all.

Build¶

Terminal 1:

source /opt/ros/$ROS_DISTRO/setup.bash
cd ~/ros2_ws
colcon build --packages-select dbpendulum_ctrl --symlink-install

Run¶

Terminal 1:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch dbpendulum_ctrl dbpendulum_ctrl.launch.py

This starts Gazebo Sim, spawns the pendulum already at the trajectory's start pose, brings up ros2_control's controller manager, and starts the control node. Link1 sweeps through a 1-rad move over 3s while link2 swings out and back over two 1.5s segments — all driven by torques computed live from the feedback-linearization law, not by directly setting joint angles.

Parameters¶

Set in config/dbpendulum_ctrl_params.yaml. The physical parameters (m1...l) describe the same physical robot as dbpendulum's dbpendulum_params.yaml; g and the gains are specific to this package:

Param Meaning Default
m1 link 1 mass 1.0
m2 link 2 mass 1.0
I1 link 1 moment of inertia about its own COM 0.1
I2 link 2 moment of inertia about its own COM 0.1
c1 pivot-to-COM distance, link 1 0.5
c2 pivot-to-COM distance, link 2 0.5
l link length 1.0
g gravity used inside the controller's model 9.8
kp1, kp2 proportional gain, joint 1 / joint 2 100.0
kd1, kd2 derivative gain, joint 1 / joint 2 20.0 (2*sqrt(kp), critically damped)

Design notes¶

  • Feedback linearization, ported directly. The control node computes T = M(theta)*(qddot_ref - Kp*(theta-theta_ref) - Kd*(thetadot-thetadot_ref)) + C(theta,thetadot) + G(theta) using the exact same M11/M12/M21/M22/C1/C2/G1/G2 closed-form expressions as twoink_main.py's control() function. Because the model terms cancel the plant's actual dynamics exactly, the tracking error settles into a simple critically-damped linear response — verified in a standalone (non-ROS2) simulation with tracking error under 1e-6 rad.
  • g is 9.8, not the reference script's illustrative 10. Feedback linearization only cancels gravity/Coriolis/inertia exactly if the controller's internal model matches the actual simulated plant — so this tracks Gazebo's real default gravity, same as dbpendulum.
  • A different joint convention than dbpendulum, on purpose. The reference script's dynamics are derived in a planar (x, y-up, theta measured from the +x axis) convention. Rather than bolt a hand-derived offset/sign correction onto dbpendulum's "hangs down along -Z" geometry, this package's URDF uses a different axis and link direction (axis="0 -1 0", links extending along local +X) chosen so the raw joint angle is theta1/theta2 in the script's exact sense, offset zero. This package's URDF is not interchangeable with dbpendulum's.
  • No JointStatePublisher gz-sim plugin, no /joint_states bridge. joint_state_broadcaster (a ros2_control controller) publishes /joint_states as a native ROS2 topic directly from the hardware state interfaces. The only gz-transport↔ROS2 bridge left is /clock.
  • Torque commands go through a plain pass-through controller. effort_controller (forward_command_controller/ForwardCommandController, interface_name: effort) does no control of its own — it just forwards the control node's [T1, T2] published on /effort_controller/commands straight to the joints. All the actual control law lives in the dbpendulum_ctrl node, not in a canned ros2_control controller.
  • Initial condition must match the trajectory's t=0. The URDF's <ros2_control> block sets each joint's initial_value to the trajectory's starting angles (theta1(0) = -pi/2 - 0.5, theta2(0) = 0). If you change the trajectory's start, update these too, or the controller will slam a large one-shot correction the instant it activates.

Troubleshooting¶

  • Pendulum snaps hard the instant control starts. The URDF's initial_value params (in <ros2_control>) don't match the trajectory generator's t=0 reference in control_node.py — keep them in sync.
  • No motion / effort commands never arrive. Check that joint_state_broadcaster and effort_controller both spawned successfully (ros2 control list_controllers) — they're chained to start only after the model spawns, so a slow Gazebo startup can delay them, not fail them.
  • Wrong torque direction / controller fights itself. This almost always means a joint axis or link-direction mismatch with the feedback-linearization model's convention — see the design note above before assuming it's a gain-tuning problem.
