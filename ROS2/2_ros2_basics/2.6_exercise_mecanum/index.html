2.6 Exercise: Mecanum Car¶

Now that you've built ddrive, ddrive_ik, and ddrive_ik_msgs for a differential-drive (unicycle) robot, repeat the exercise for a mecanum-wheel car — a holonomic robot that can move in any direction without needing to rotate first.

The model¶

ddrive's unicycle model couples heading and motion — the robot can only move along the direction it's currently facing:

xdot     = v * cos(theta)
ydot     = v * sin(theta)
thetadot = omega

A mecanum (holonomic) drive decouples them. For this exercise, use the simplified model:

xdot = vx
ydot = vy

where vx and vy are commanded velocities in the world frame, independent of any heading. (If you want to go further, add a theta state and thetadot = omega back in, and decide for yourself whether vx/vy should be interpreted in the world frame or the robot's body frame — mecanum wheels genuinely support both, and the difference is a good thing to reason through.)

What to build¶

Mirror the ddrive package structure:

ddrive_mecanum/
├── package.xml
├── setup.py
├── setup.cfg
├── resource/ddrive_mecanum
├── config/
│   └── params.yaml
├── launch/
│   └── ddrive_mecanum_launch.py
└── ddrive_mecanum/
    ├── __init__.py
    ├── kinematics.py     # your new xdot=vx, ydot=vy integrator
    ├── sim_node.py        # subscribes /cmd_vel, integrates, publishes /pose
    └── viz_node.py         # same matplotlib visualization as ddrive_viz

/cmd_vel is still a geometry_msgs/Twist — just interpret linear.x/linear.y as vx/vy instead of linear.x/angular.z as v/omega.

Suggested steps¶

  1. Kinematics first, no ROS. Write and test euler_step(z, u, dt) for the new model as a plain Python function, same as ddrive's kinematics.py — verify it moves diagonally when vx and vy are both nonzero, and that it's genuinely decoupled from heading.
  2. Wrap it in a node. Copy sim_node.py from ddrive and swap in the new kinematics.
  3. Reuse the visualizer. ddrive_viz's drawing code barely needs to change — a circle plus a heading line still works, even if heading is now cosmetic rather than driving the motion.
  4. Drive it. Command diagonal, sideways, and combined motions and confirm the robot actually moves in directions a unicycle robot couldn't reach without turning first: 
    ros2 topic pub /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.3, y: 0.3}}" -r 10
  5. Collapse into a launch file, same pattern as ddrive_launch.py.

Stretch goals¶

  • Add ddrive_ik-style trajectory tracking on top: pick a reference curve and a control law that works for a fully decoupled (x, y) system — it should end up simpler than the point-offset feedback-linearization trick ddrive_ik needed, since there's no heading coupling to work around.
  • Add the theta/omega state back in and support commanding heading independently of translation.
  • Add a ResetPose service, same pattern as ddrive_ik_msgs.

Deliverables¶

  • [ ] kinematics.py with a working euler_step for the new model
  • [ ] sim_node.py + viz_node.py running and visibly moving
  • [ ] A launch file that brings both up together
  • [ ] A short write-up (a few sentences) of what changed vs. ddrive and why — this is the point of the exercise, not just working code
