2.1 Fundamentals¶

From Python functions to ROS 2¶

If you already know Python, one useful way to understand ROS 2 is to start with something familiar: functions.

A normal Python program might look like this:

def main():
    x = read_sensor()
    u = controller(x)
    send_command(u)

The programmer controls the sequence. main() calls one function, which calls another, and the program proceeds step by step.

A robot is different.

A robot operates in the real world, where time keeps moving. Sensors continuously produce data, controllers continuously compute commands, and other parts of the system need to keep running.

ROS 2 provides a way to organize this continuous computation.

A ROS 2 node can be thought of as an active computational program that stays alive and responds to events.

This is not a literal definition of a node, but it is a useful mental model when coming from traditional Python programming.

1. Nodes: active computational blocks¶

A node is a running ROS 2 program that performs a particular responsibility.

For a differential-drive robot, you might have:

  • a localization node that estimates the robot's position,
  • a planner node that determines a path,
  • a controller node that computes velocity commands,
  • a simulator node that moves the robot,
  • a visualization node that displays the robot's state.

Each node can operate independently.

This is different from a traditional program in which functions are called directly:

Traditional Python

main()
  |
  +--> localization()
  |
  +--> planner()
  |
  +--> controller()

In ROS 2, the components are independent:

ROS 2

Localization node  --->  topic  --->  Controller node
                                           |
                                           | topic
                                           v
                                      Simulator node

The nodes do not need to directly call one another.

They communicate through ROS 2's communication mechanisms.

A node is more than one function¶

The analogy to a function is useful, but a node is not literally a function.

A Python ROS 2 node is commonly implemented as a class containing several functions, such as:

  • subscriber callback functions,
  • timer callback functions,
  • service callback functions,
  • action callbacks.

The node stays alive, while ROS 2 calls the appropriate function when something happens.

For example, a controller might have a callback that executes whenever a new robot pose arrives:

new pose arrives
      |
      v
controller callback()
      |
      +--> compute control
      |
      +--> publish cmd_vel

So a useful mental model is:

A node is an active computational block containing functions that respond to events.

2. Topics: communication channels¶

A topic is a named communication channel.

Topics do not perform the computation themselves. They carry messages between nodes.

Think of the analogy with a traditional function:

Python function

input --> function --> output

In ROS 2:

Node A --> topic --> Node B

The topic is like the connection between the two computational blocks.

For example, a localization node might publish the robot's estimated position on the odom topic:

Localization node
       |
       | publishes pose
       v
     /odom
       |
       | subscribed by
       v
Controller node

The controller does not directly call the localization node.

It simply subscribes to /odom.

This separation is important because the publisher does not need to know who is listening.

Topics are asynchronous¶

ROS 2 communication is generally asynchronous.

A publisher sends a message when it has one.

A subscriber receives it and ROS 2 schedules the appropriate callback.

The two nodes do not have to execute at exactly the same time.

This is different from a normal Python function call, where the caller waits for the function to execute and return.

3. Messages: the data being exchanged¶

A message defines the type and structure of data being sent on a topic.

For example, a topic might carry:

  • a position,
  • a velocity,
  • a laser scan,
  • an image,
  • an IMU measurement,
  • a robot pose.

You can think of the message as the data structure being passed between computational blocks.

For example:

/odom
  |
  |  Odometry message
  v
Controller

The topic tells us where the data is being communicated.

The message tells us what the data looks like.

This distinction is important:

Topic = communication channel.
Message = data carried by the channel.

4. Publishers and subscribers¶

A node uses a publisher to send messages to a topic.

A node uses a subscriber to receive messages from a topic.

For example, consider a differential-drive controller.

It needs two inputs:

  1. The current robot pose.
  2. The desired goal.

It produces one output:

  1. A velocity command.

Conceptually:

             /odom
               |
               v
        +--------------+
        |              |
/goal ->|  Controller  |-> /cmd_vel
        |              |
        +--------------+

The controller:

  • subscribes to /odom,
  • subscribes to /goal,
  • computes the control command,
  • publishes to /cmd_vel.

A node can have:

  • many inputs and outputs,
  • only inputs,
  • only outputs,
  • or neither.

For example, a node that only displays information might only subscribe to topics.

A node that generates a fixed command might only publish.

5. Callbacks: where the computation happens¶

The actual robotics computation still happens in your Python code.

ROS 2 does not replace your equations.

Suppose your controller uses:

heading_error = desired_heading - current_heading

and then computes a velocity command.

That calculation can be ordinary Python.

The difference is how the data gets into and out of the function.

In a traditional program:

pose = get_pose()
goal = get_goal()

command = controller(pose, goal)

In ROS 2:

/odom ----\
           \
            -> controller callback -> /cmd_vel
           /
/goal ----/

ROS 2 calls the callback when the relevant events occur.

This is why ROS 2 is often described as event-driven.

6. Services: request and response¶

Topics are useful when information is continuously exchanged.

But sometimes we want to ask a node to do something and receive a response.

That is a service.

A useful analogy is:

A service is similar to calling a function on another node.

For example:

reset_simulation()

The request might be:

"Reset the robot."

The response might be:

"Reset successful."

Unlike a topic, the interaction is explicitly:

request
   |
   v
service
   |
   v
response

Services are useful for short operations where we expect a response.

Examples include:

  • resetting a simulator,
  • requesting a calculation,
  • changing a simple state,
  • triggering a short operation.

Services are not primarily for starting and stopping nodes. Node lifecycle and process management are handled through other ROS 2 mechanisms.

7. Actions: long-running tasks¶

What if the request takes a long time?

Suppose we tell the robot:

"Drive to this goal."

The robot might need 30 seconds.

A simple service is not ideal because we want to know what is happening while the task is running.

An action is designed for this type of problem.

An action can provide:

  • a goal,
  • feedback while the goal is executing,
  • a final result,
  • the ability to cancel the goal.

Conceptually:

             goal
              |
              v
        +-------------+
        |   Action    |
        +-------------+
              |
        feedback
              |
              v
        20% ... 50% ... 90%
              |
              v
            result

For example:

"Drive to X = 5, Y = 3."

       ↓

"Goal accepted."

       ↓

"30% complete."

       ↓

"70% complete."

       ↓

"Goal reached."

This makes actions particularly useful for navigation and manipulation tasks.

A simple way to remember the three communication patterns is:

Topic: exchange information.
Service: request something and get a response.
Action: request a task that takes time and receive feedback.

8. Parameters: configurable variables¶

A ROS 2 parameter is a configurable value associated with a node.

For example, a controller might have:

maximum_speed = 1.0
Kp = 2.0
heading_tolerance = 0.05

Instead of hard-coding these values into the program, we can expose them as ROS parameters.

The important idea is:

Parameters allow us to configure a node without changing its source code.

For example, we might run the same controller with different values of Kp.

Parameters are similar to variables in your program, but it is more accurate to think of them as externally configurable settings belonging to a node.

9. Packages: organizing the software¶

A package is a unit of ROS 2 software organization.

A package can contain:

  • Python nodes,
  • Python modules,
  • launch files,
  • configuration files,
  • message definitions,
  • service definitions,
  • action definitions,
  • robot descriptions,
  • other resources.

A package might contain one node or many nodes.

For example:

ddrive package

    controller node
    localization node
    simulator node
    planner node
    launch file
    configuration files

The package is therefore closer to a software project than to a single function.

10. Building a package¶

After creating or modifying ROS 2 software, we commonly use:

colcon build

The build process prepares the packages in the workspace so they can be used by ROS 2.

A useful distinction is:

Build = prepare the software.

You do not necessarily build only once for the lifetime of a package.

You rebuild when you make changes that require rebuilding.

For example, adding a package or changing package configuration requires a build.

11. Sourcing a workspace¶

After building, we commonly run:

source install/setup.bash

source does not build the package.

Instead, it runs the setup script inside your current terminal shell.

The setup script changes environment variables so that your terminal knows where your ROS 2 packages, executables, Python modules, and libraries are located.

A useful mental model is:

Build = prepare the software.
Source = tell this terminal where the software is.
Run = start the software.

You normally need to source the workspace in each new terminal where you want to use that workspace.

12. Running nodes manually¶

Suppose the ddrive package contains a controller node.

After sourcing the workspace, we might run:

ros2 run ddrive controller

This starts the controller node.

If we have several nodes, we could start them individually.

For example:

ros2 run ddrive localization
ros2 run ddrive planner
ros2 run ddrive controller
ros2 run ddrive simulator

This is useful while learning and debugging.

However, manually starting a large robot system becomes inconvenient.

13. Launch files¶

A launch file allows us to start multiple nodes and configure them together.

Instead of manually starting:

localization
planner
controller
simulator
visualization

we can create one launch file.

Then we can run:

ros2 launch ddrive robot.launch.py

The launch system starts the required nodes.

Conceptually:

                  Launch file
                      |
       +--------------+--------------+
       |              |              |
       v              v              v
 Localization      Planner       Controller
                                      |
                                      v
                                  Simulator

This is how a real robot system can be started with a single command.

Important clarification¶

You do not need one terminal for every node.

You can run multiple processes from a terminal, and launch files can start many nodes for you.

The point of a launch file is not simply to avoid opening many terminals. It also lets you specify how the nodes should be configured, which parameters they use, what other resources they need, and how the overall system should start.

Putting everything together¶

Let's return to our differential-drive robot.

Suppose we want to drive from a starting point to a goal.

We might have:

                 /goal
                   |
                   v
             +-----------+
             |  Planner  |
             +-----------+
                   |
                 /path
                   |
                   v
             +-----------+
 /odom ----> | Controller| ----> /cmd_vel
             +-----------+
                                  |
                                  v
                           +-------------+
                           |  Simulator  |
                           +-------------+
                                  |
                                /odom
                                  |
                                  +----> Controller

The important point is that ROS 2 does not provide the robotics equations automatically.

Your controller still contains your control law.

Your planner still contains your planning algorithm.

Your simulator still contains the differential-drive equations.

For example, the simulator might integrate:

x_dot     = v cos(theta)
y_dot     = v sin(theta)
theta_dot = omega

ROS 2 provides the software architecture that allows these computational components to communicate.

The big picture¶

Traditional Python programming often looks like:

main()
  |
  +--> function A
  |
  +--> function B
  |
  +--> function C

ROS 2 turns this into a collection of independent computational components:

             topic
Node A ----------------> Node B
  |                       |
  |                       |
  v                       v
topic                    topic
  |                       |
  +-------> Node C <------+

So the conceptual progression is:

Function

→ a piece of code that performs a computation.

Node

→ an active computational component that stays alive.

Callback

→ a function inside a node that ROS 2 invokes when an event occurs.

Topic

→ a communication channel between nodes.

Message

→ the data traveling through the channel.

Service

→ a request-response interaction.

Action

→ a long-running, feedback-enabled task.

Parameter

→ a configurable value associated with a node.

Package

→ an organized unit of ROS 2 software.

Launch file

→ a way to start and configure a collection of nodes as a system.

This gives us the foundation we need for the next step: building the ddrive package and seeing how these concepts become actual Python code.
