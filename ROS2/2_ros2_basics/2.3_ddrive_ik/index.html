2.3 ddrive_ik: Trajectory Tracking¶

Package download

Download ddrive_ik.zip

ddrive_ik adds trajectory tracking on top of ddrive — it does not duplicate ddrive_sim or ddrive_viz, it depends on them.

Node Package Subscribes Publishes
ddrive_sim ddrive /cmd_vel /pose
ddrive_viz ddrive /pose —
ddrive_trajectory ddrive_ik — /reference
ddrive_controller ddrive_ik /pose, /reference /cmd_vel

0. Install (build order matters here)¶

Both packages need to be in the same workspace, and ddrive needs to build first since ddrive_ik depends on it:

cp -r ddrive ~/ros2_ws/src/          # if not already there
cp -r ddrive_ik ~/ros2_ws/src/
cd ~/ros2_ws
source /opt/ros/$ROS_DISTRO/setup.bash
rosdep install --from-paths src --ignore-src -r -y
colcon build --packages-select ddrive ddrive_ik
source install/setup.bash

colcon figures out the build order itself from ddrive_ik/package.xml declaring ddrive as an exec_depend — you don't have to specify it.

Checkpoint:

ros2 pkg executables ddrive_ik

should list ddrive_ik ddrive_trajectory and ddrive_ik ddrive_controller.

1. What's new here¶

ddrive_ik/
├── package.xml           # exec_depend on rclpy, geometry_msgs, AND ddrive
├── setup.py
├── config/
│   ├── params.yaml         # this package's own two nodes
│   └── tracking_params.yaml  # all three timed nodes, including ddrive_sim
├── launch/
│   └── tracking_launch.py  # starts nodes from BOTH ddrive and ddrive_ik
└── ddrive_ik/
    ├── kinematics.py       # point-offset transforms + control law
    ├── trajectories.py     # astroid / circle reference curves
    ├── trajectory_node.py  # ddrive_trajectory
    └── controller_node.py  # ddrive_controller

This is a different kinematics.py than the one in ddrive — that one has the forward-kinematics integrator; this one has the tracking control law. They're never ambiguous because the package name is part of the import path: ddrive.kinematics vs. ddrive_ik.kinematics.

2. Run it¶

Terminal by terminal (4 terminals)¶

The robot needs to start where the reference curve starts, or the controller's first correction is huge (see the debugging note below). For the default astroid (scale=1.0, px=0.05, py=0.0), that start point is x0=0.95, y0=0.0, theta0=0.0.

Terminal 1 — simulator, seeded to match the curve:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive ddrive_sim --ros-args -p x0:=0.95 -p y0:=0.0 -p theta0:=0.0 -p dt:=0.01

Terminal 2 — visualizer:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive ddrive_viz

Terminal 3 — trajectory generator:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive_ik ddrive_trajectory --ros-args -p dt:=0.01

Nothing moves yet — confirm it's publishing:

ros2 topic echo /reference

Terminal 4 — controller:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive_ik ddrive_controller --ros-args -p dt:=0.01

The robot should ease onto the astroid and trace it continuously, looping every 10 seconds.

Collapsed into one launch file¶

ros2 launch ddrive_ik tracking_launch.py

No arguments needed — the seeded start pose and dt=0.01 are already the defaults. Try other shapes/gains:

ros2 launch ddrive_ik tracking_launch.py shape:=circle period:=6.0
ros2 launch ddrive_ik tracking_launch.py Kp:=20.0

If you change scale, px, or py, recompute the seed pose: x0 = scale - px, y0 = -py, theta0 = 0 (the curve always starts at point P = (scale, 0) at t=0).

3. Look at the graph — now spanning two packages¶

ros2 node list

shows all four nodes with no indication of which package each came from — worth pointing out explicitly, since it's the clearest proof that packages are a build-time/filesystem concept, not a runtime one.

ros2 pkg executables ddrive
ros2 pkg executables ddrive_ik

confirms the split: ddrive_ik genuinely does not contain ddrive_sim.

4. New functions¶

point_C_to_P / point_P_to_C convert between the robot's center C and a controlled point P offset by (px, py) in the robot's body frame — same as the original script's ptC_to_ptP / ptP_to_ptC:

def point_C_to_P(z, px, py):
    x_c, y_c, theta = z
    cos, sin = math.cos(theta), math.sin(theta)
    x_p = x_c + px * cos - py * sin
    y_p = y_c + px * sin + py * cos
    return [x_p, y_p]

feedback_linearize is the point-offset feedback-linearization control law — given the position error of point P and a gain Kp, it returns [v, omega]:

def feedback_linearize(error, theta, px, py, Kp):
    bx, by = Kp * error[0], Kp * error[1]
    cos, sin = math.cos(theta), math.sin(theta)
    a11 = cos - (py / px) * sin
    a12 = sin + (py / px) * cos
    a21 = -(1.0 / px) * sin
    a22 = (1.0 / px) * cos
    v = a11 * bx + a12 * by
    omega = a21 * bx + a22 * by
    return [v, omega]

trajectories.astroid / trajectories.circle are closed-form reference curves evaluated fresh every tick (not a precomputed array like the original script), with elapsed time wrapped modulo period so the curve repeats forever:

def astroid(t, period, a=1.0, x_center=0.0, y_center=0.0):
    phase = 2 * math.pi * t / period
    x = x_center + a * math.cos(phase) ** 3
    y = y_center + a * math.sin(phase) ** 3
    return [x, y]

5. Parameters¶

Node Parameter Default Meaning
ddrive_trajectory shape astroid astroid or circle
ddrive_trajectory period 10.0 seconds for one full loop
ddrive_trajectory scale 1.0 astroid "a" / circle radius
ddrive_controller px, py 0.05, 0.0 body-frame offset of point P
ddrive_controller Kp 100.0 proportional gain

Two YAML files ship in config/:

params.yaml covers this package's own two nodes:

ddrive_trajectory:
  ros__parameters:
    dt: 0.01
    shape: astroid
    period: 10.0
    scale: 1.0

ddrive_controller:
  ros__parameters:
    dt: 0.01
    px: 0.05
    py: 0.0
    Kp: 100.0

tracking_params.yaml additionally configures ddrive_sim — even though that node is defined in the other package. A params file matches by node name, not by package, same as topics:

ddrive_sim:
  ros__parameters:
    dt: 0.01
    x0: 0.95
    y0: 0.0
    theta0: 0.0

Load it with --params-file pointed at the installed copy:

ros2 run ddrive_ik ddrive_controller --ros-args --params-file \
  ~/ros2_ws/install/ddrive_ik/share/ddrive_ik/config/tracking_params.yaml

6. Debugging note: the instability, and why¶

Worth walking through with students, since it's a real failure mode, not a hypothetical one. Early on this exact controller went unstable — robot flying off to huge coordinates within a couple of seconds.

The control law is designed so the tracking error decays as edot ≈ -Kp · e in continuous time. Euler-discretized at step dt, that becomes:

e[n+1] = e[n] · (1 - Kp·dt)

This only decays if 0 < Kp·dt < 2. With Kp=100 and dt=0.1 (the original default, copied from the FK example), Kp·dt = 10 — way outside that range, and the error flips sign and grows 9x every step. The original plain-Python script never hit this because it integrated at dt=0.01, giving Kp·dt = 1.

Fix: either lower dt (now the default, 0.01) or lower Kp to keep the product under 2. Confirmed numerically:

# Kp*dt = 10 -> diverges to ~1e32 within 5 simulated seconds
# Kp*dt = 1  -> stays bounded, tracks the curve

A second, independent cause of instability: starting the robot far from where the reference curve begins produces a large initial error, which a high-gain controller reacts to violently on the very first step. This is why the simulator is seeded to (0.95, 0, 0) — matching the curve's own start — rather than the default (0, 0, 0).
