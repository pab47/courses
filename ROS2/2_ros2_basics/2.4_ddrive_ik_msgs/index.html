2.4 ddrive_ik_msgs: Services & Actions¶

Package download

Download ddrive_ik_msgs.zip

Everything so far — ddrive and ddrive_ik — communicates entirely through topics: /pose, /cmd_vel, /reference. Topics are one of three ways ROS 2 nodes talk to each other. This page covers the other two, in three parts: the concepts, the interface definitions, and then the actual service/action code wired into ddrive and ddrive_ik.

Part 1 — Concepts: topics vs. services vs. actions¶

Topic (what you've used) Service Action
Pattern publish/subscribe request → response goal → feedback → result
Who talks to whom many-to-many one client, one server one client, one server
Blocking? never — fire and forget client waits for the response client gets progress updates, doesn't block
Duration ongoing stream fast, bounded (milliseconds) can take a long time
Cancelable mid-way? n/a no yes
Feedback while running? n/a no yes
Real-world example /cmd_vel, /pose "add two ints", "reset the map" "navigate to this pose" (nav2)

The intuition: topics are for continuous state that keeps flowing whether or not anyone's listening. Services are for "ask a quick, well-defined question, get one answer" — a function call over the network. Actions are for "start a task that takes a while, tell me how it's going, let me cancel it" — and are actually built on top of services and topics under the hood (a goal service, a cancel service, a result service, plus a feedback topic and a status topic).

Beginner vs. Intermediate

The official ROS 2 tutorials cover services in the Beginner series, right after topics. Actions are Intermediate. If you're following the tutorials in order, services come next; actions are a reasonable stretch beyond that, not a beginner-series gap.

Where these fit into this course:

  • ResetPose (service) — snaps ddrive_sim's pose to a given (x, y, theta) instantly. A service fits because resetting has a definite, immediate answer ("done" or "failed") — the same shape as "add two ints," just for this robot.
  • TrackTrajectory (action) — track the reference curve for a bounded number of loops, with feedback (loops completed, current error) published as it runs, and a result (total time, final error) when it finishes — cancelable mid-run. This is the first place in the course where a topic-only design genuinely falls short: ddrive_controller tracks forever, with no way to say "and stop after this" or "how's it going so far."

Part 2 — The interface definitions¶

Every node so far is an ament_python package. Generating real message classes from .srv/.action files requires rosidl_generate_interfaces, which only runs inside an ament_cmake package — a hard ROS 2 constraint, not a style choice. So ddrive_ik_msgs exists purely to hold these two definitions; it has no Python code, no nodes, nothing to ros2 run on its own.

ddrive_ik_msgs/
├── package.xml         # ament_cmake, not ament_python
├── CMakeLists.txt       # calls rosidl_generate_interfaces
├── srv/
│   └── ResetPose.srv
└── action/
    └── TrackTrajectory.action

ResetPose.srv — request above ---, response below:

float64 x
float64 y
float64 theta
---
bool success
string message

TrackTrajectory.action — three blocks: goal, result, feedback:

int32 num_loops
---
float64 total_time
float64 final_error
---
int32 loops_completed
float64 current_error

CMakeLists.txt:

cmake_minimum_required(VERSION 3.8)
project(ddrive_ik_msgs)

find_package(ament_cmake REQUIRED)
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "srv/ResetPose.srv"
  "action/TrackTrajectory.action"
)

ament_package()

Build it on its own first, before wiring anything to it:

cp -r ddrive_ik_msgs ~/ros2_ws/src/
cd ~/ros2_ws
source /opt/ros/$ROS_DISTRO/setup.bash
colcon build --packages-select ddrive_ik_msgs
source install/setup.bash

Checkpoint:

ros2 interface show ddrive_ik_msgs/srv/ResetPose
ros2 interface show ddrive_ik_msgs/action/TrackTrajectory

Part 3 — Using them: ResetPose (ddrive) and TrackTrajectory (ddrive_ik)¶

Both ddrive and ddrive_ik now depend on ddrive_ik_msgs — the same exec_depend pattern ddrive_ik already used for ddrive, just one more package added to the graph:

<exec_depend>ddrive_ik_msgs</exec_depend>

ResetPose — service server in ddrive_sim¶

The server lives in ddrive_sim (package ddrive) because that's the node that actually owns the pose state z. The callback just overwrites it and reports success:

from ddrive_ik_msgs.srv import ResetPose

self.create_service(ResetPose, 'reset_pose', self._reset_pose_cb)

def _reset_pose_cb(self, request, response):
    self._z = [request.x, request.y, request.theta]
    response.success = True
    response.message = f'pose reset to x={request.x}, y={request.y}, theta={request.theta}'
    return response

Get ddrive_sim running first — /reset_pose only exists while that node is up. Easiest way is the launch file from the ddrive page, which brings up ddrive_sim + ddrive_viz together:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch ddrive ddrive_launch.py

(Two separate ros2 run terminals for ddrive_sim and ddrive_viz work just as well, if you'd rather see them as separate processes — see Stage 1 on the ddrive page.)

Checkpoint before calling the service — confirm it actually exists: 

ros2 service list | grep reset_pose

With that running, a small client, ddrive_reset_pose_client, calls it once and exits — unlike a node, a service client doesn't need an ongoing relationship with anything:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive ddrive_reset_pose_client 0.95 0.0 0.0

Watch the plot window jump to (0.95, 0) the instant the client call returns. You can also call it directly from the CLI, no client code needed:

ros2 service call /reset_pose ddrive_ik_msgs/srv/ResetPose "{x: 0.0, y: 0.0, theta: 0.0}"

TrackTrajectory — action server in ddrive_ik¶

This one lives in a new node, ddrive_track_action_server, in ddrive_ik — deliberately not folded into ddrive_controller. The action server only watches /pose and /reference (the same topics ddrive_controller already uses) and reports progress; it never publishes /cmd_vel itself. ddrive_controller keeps tracking forever regardless of whether any action goal is active — the action just adds a bounded, observable "session" on top of that endless process:

self._action_server = ActionServer(
    self, TrackTrajectory, 'track_trajectory',
    execute_callback=self._execute_cb,
    goal_callback=self._goal_cb,
    cancel_callback=self._cancel_cb,
)

def _execute_cb(self, goal_handle):
    num_loops = goal_handle.request.num_loops
    total_duration = num_loops * self._period
    start = time.monotonic()

    while (time.monotonic() - start) < total_duration:
        if goal_handle.is_cancel_requested:
            goal_handle.canceled()
            ...  # return an early Result
        feedback.loops_completed = int((time.monotonic() - start) // self._period)
        feedback.current_error = self._current_error()
        goal_handle.publish_feedback(feedback)
        time.sleep(0.5)

    goal_handle.succeed()
    ...  # return the final Result

Why MultiThreadedExecutor

_execute_cb blocks on time.sleep() while polling for cancellation. With the default single-threaded executor, a cancel request would never get processed while that sleep is happening — so main() spins this node with a MultiThreadedExecutor instead, matching the official rclpy action tutorial's guidance.

Get everything running first — the action server needs /pose and /reference actually flowing (from ddrive_sim and ddrive_trajectory) to report a meaningful current_error, and ddrive_controller needs to be running for the robot to actually move. tracking_launch.py now starts all five nodes together, including ddrive_track_action_server:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch ddrive_ik tracking_launch.py

(Terminal-by-terminal works too, if you'd rather see each node start separately — see Run it, terminal by terminal on the ddrive_ik page, then add a 5th terminal for ddrive_track_action_server on top of those four.)

Checkpoint before sending a goal — confirm the action actually exists: 

ros2 action list
should include /track_trajectory.

With that running, the client, ddrive_track_action_client, sends a goal, prints feedback as it streams in, and sends a cancel request on Ctrl+C instead of just quitting:

source /opt/ros/$ROS_DISTRO/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 run ddrive_ik ddrive_track_action_client 2

This should print a feedback: line roughly every half second showing loops_completed climbing and current_error fluctuating as the robot tracks, then a result: line once 2 full loops complete. Ctrl+C partway through and confirm the action server's terminal logs goal canceled instead of goal succeeded.

You can also send a goal without any client code:

ros2 action send_goal /track_trajectory ddrive_ik_msgs/action/TrackTrajectory "{num_loops: 1}" --feedback

Build both packages with the new dependency¶

cd ~/ros2_ws
rm -rf build/ddrive build/ddrive_ik install/ddrive install/ddrive_ik log
source /opt/ros/$ROS_DISTRO/setup.bash
colcon build --packages-select ddrive ddrive_ik
source install/setup.bash
